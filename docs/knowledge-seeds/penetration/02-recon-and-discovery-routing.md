# 侦察与 Web 资产发现工具路由

## 路由原则

工具选择应由当前缺失的事实驱动。先选择低成本、低影响的探测，再根据结果逐步扩大覆盖。

## 网络与服务发现

### nmap

适合主机、端口、服务和版本发现。输入应是授权主机或 IP。输出中的开放端口和服务版本是后续
Web 探测、中间件识别和专项验证的基础。若只知道一个 URL，但怀疑存在非 Web 管理端口，可对
同一授权主机补充端口扫描。不要把端口号直接等同于产品。

推荐后续动作：

- 发现 80、443 或其他 HTTP 服务：交给 `httpx`；
- 发现 7001/7002 且服务证据指向 WebLogic：补充 HTTP 与 T3/IIOP 识别；
- 发现 8080/8443：先识别具体容器或应用，不直接假定 Tomcat；
- 发现数据库端口：记录暴露面，除非范围明确允许，否则不进行口令尝试。

### httpx

适合确认 Web 可达性、最终跳转、状态码、标题、Web Server 和技术栈。应优先使用最终 URL 作为
后续爬取入口，并检查跨主机跳转是否越界。状态码 401/403 表示入口存在，不等于不可测试；应
记录认证边界，而不是自动爆破。

### whatweb-fingerprint 与 ehole

用于补充框架、CMS、中间件和前端技术指纹。指纹只能作为路由提示：

- 多个独立信号一致时提高置信度；
- 仅有 Header 或页面关键词时保持“候选”状态；
- 指纹冲突时，以可复现响应、静态资源路径和版本证据为准。

## 路径和接口发现

### katana

适合从真实页面、脚本和表单中发现 URL。默认深度应保持有限，并过滤静态资源。React、Vue、
Angular 等前端应用可启用 JavaScript 解析，但仍需控制抓取时间和并发。Katana 结果应进入共享
discovery 目录，再由 `dispatcher` 分片给 `nuclei`，避免每个工具重复抓取。

### dirsearch 与 ffuf-dir-enum

用于补充爬虫无法发现的目录、管理入口、备份文件和接口路径。选择原则：

- 已知 Java 技术栈时优先 JSP、action、do、api、admin 等语义词典；
- 已知 PHP 技术栈时补充 PHP 和框架常用路径；
- 已有路径种子时优先围绕种子扩展，不进行无限递归；
- 对 301、302、401、403 结果保留证据，但需要进一步确认是否为统一拦截页。

同一路径字典和同一入口在没有新指纹时不应重复执行。

## 推荐组合

### 只有 IP

`nmap → httpx → whatweb/ehole → katana → dispatcher → nuclei`

### 已知 Web URL

`httpx → whatweb/ehole → katana → dirsearch/ffuf（按需）→ dispatcher → nuclei`

### SPA 或 API 应用

`httpx → katana(JavaScript) → API 路径归一化 → 参数和认证边界分析 → 专项验证`

### 中间件管理面

`nmap → httpx → 产品/版本确认 → 管理路径检查 → 对应框架 safe-poc`

## 有效发现的判定

一条发现应至少包含 URL 或主机端口、状态、来源工具和时间。路径只出现在字典中不算发现；必须
有真实响应。相同内容的泛化 200 页面、WAF 拦截页和统一 404 页面应去重，避免污染后续扫描。
